## 2. 一句话结论

0.59 已形成一个方向正确的批量观察、精确匹配、downside 筛选和 Seller OS
策略骨架，但当前真实运行只有 `0 observed / 0 exact_matched / 0 pilot_ready`，六个
Seller OS 页面在交付 Web 中全部 404，用户无法从“发现机会”完成到
Passport、内容草稿、独立批准、Pilot、Readback 和现金对账；套餐只是代码常量，没有
用量账、增购路径或商业验收。因此本轮 **REJECTED**。

在所有 P0 关闭、`P1-PM-01` 修复并完成 PM 复审前，本结论不得改为
`APPROVED`。

### 3.2 建议冻结的首发 JTBD

首发 JTBD 应收敛为：

> 当中国 Ozon 卖家每天面对大量 Ozon/1688 线索时，帮助经营负责人在不伪造销量和
> 实际利润的前提下，快速识别值得补证的精确 SKU，完成可追溯内容草稿和 1–3 件

当前实现覆盖了“批量筛选”前半段，但没有把该 JTBD 的后半段做成用户可完成的产品

## 5. 六经营模式评审

代码定义了六种模式：

1. `controlled_distribution`
2. `refined_operation`
3. `hero_sku`
4. `brand_building`
5. `store_cluster`
6. `hybrid`

模式分类逻辑具备 downside CM3、结算周期、置信度、品牌授权和多主体条件，但当前 Web
诊断只提交空的 `operating_facts`，所以策略必然缺 downside 与置信度。即使服务端返回
`blocked`，页面仍会显示一个 `operating_mode`，通知还写“事实分类完成”，没有向用户
解释该模式不可执行。这会把默认回退值误读为经营建议。

六模式还缺：

- 每个模式的目标客户、进入条件、退出条件、关键动作、反向指标和最大损失。
- 从当前模式切换到下一模式所需 Evidence、Owner 和预计周期。
- 同一 SKU 在不同模式下的预算、库存、内容、广告与回读差异。
- 模式效果的真实 cohort、对照和结算后收益证据。

结论：模式分类可作为内部策略候选，尚不能作为客户购买或经营决策功能放行。

## 12. Findings

### P0

#### P0-PM-01：六个核心商业页面未进入当前交付物

实际 Web 容器对六个目标路由全部返回 404；当前运行 OpenAPI/版本控制 OpenAPI 也未与
Seller OS 路由一致。源码存在不能替代可访问页面和合同。

处理：`auto-fix`。重新构建交付镜像，统一运行 OpenAPI 与版本化合同，验证六路由 200、
鉴权、真实/`no_data` 响应，并保存浏览器 Evidence。

#### P0-PM-02：用户无法完成从机会到现金对账的首发 JTBD

批量页只有扫描和静态 next action；六页没有到 Passport、Content、Approval、
Execution、Readback 和 Reconciliation 的连续任务入口。当前真实 run 为全零，也没有
首个真实 Pilot 或结算闭环。

处理：`ask-user` 冻结首发 ICP/JTBD，随后 `auto-fix` 端到端导航和任务合同。至少用一个
真实 SKU 完成 observe → draft → approved pilot → readback → reconcile，再申请复审。

#### P0-PM-03：当前套餐不可交易、不可计量、不可增购

固定价格卡没有版本化商业决策、订阅/账单/usage ledger、配额行为、增购或升级路径。
目前公开价格会造成“已经可买”的错误预期。

处理：`defer` 公开售卖，或在页面明确标记“内部定价假设/不可购买”；若本版本要求售卖，
则必须补完整计费与用量合同并提供沙箱验收。

#### P0-PM/RA-07：Ozon Listing 未按 exact identity + variant 聚合 cohort

`BatchOpportunityWorkspace.prepare()` 读取 Ozon 全量 observation，`_scan()` 对每条
Ozon observation 分别产生 match；`MarketplaceObservationWorkspace.latest()` 只按
observation fingerprint 去重，不按 `store_ref + exact product identity + exact variant`
选择同一 Listing 的当前事实。相同 SKU 的不同快照/价格/来源可成为多行候选，导致
`exact_matched`、排序、价格带和策略分布重复计算；`matched_keys` 又只按
`candidate_key` 集合计算未匹配数，进一步掩盖重复 cohort。

此外供应端直接选择同一 key 的最低展示 checkout 值，没有把 quantity/MOQ/税费/
境内运费边界归一为可比较 cohort 后再选择。该问题会改变选品结论和预算，不能在 PM
Gate 中降级为展示瑕疵。

处理：`auto-fix`。服务端先建立版本化 cohort key，明确 listing 最新性、店铺作用域、
exact variant 与可比购买数量；输出 raw observations、unique listings、exact cohorts、
duplicates/superseded 各自计数，并补重复快照、跨店、同变体不同 MOQ 的验收。

#### P0-PM-09：`pilot_limit` 合同未执行 selected / waitlist

`pilot_limit` 当前仅在入口校验并写入 payload；后续不参与候选选择、排序截断或
`pilot_ready` 计数。用户传入 `pilot_limit=1` 时，多个 ready 候选仍都可显示为 Pilot，
也没有 `selected`、`waitlist`、超额原因或稳定批次顺序。这使风险预算和套餐批次包络
成为假合同。

处理：`auto-fix`。在服务端对冻结排序应用 `pilot_limit`，分别输出
`eligible / selected / waitlist / rejected`，保证 selected 不超过 limit，重放顺序稳定，
并验证候选变化、并列分数、预算不足和 limit 缩小时的语义。

#### P0-PM-13：成熟度 confidence 可由任意文本凑成 1.00

成熟度分类把八个字段“非空”当作完整事实，`risk_tolerance`、`brand_maturity`、
`ops_capability` 接受任意文本；后三项并未进入分类阈值，但只要填任意字符串，
confidence 就成为 `1.00`。该值实际是表单完成率，却在页面被展示为分类置信度，会误导
预算、审批层和商业包判断。

处理：`auto-fix`。使用版本化枚举和可验证事实；分别报告
`input_completeness / evidence_coverage / classification_confidence`，不能用完成率冒充
置信度；无 Evidence 的主观输入必须降低或阻断对应决策。

#### P0-PM-14：Rule Advantage “受影响 SKU”由前端伪造

规则优势页把“需重评”直接显示为 `batch.counts.exact_matched`，没有旧/新 registry
diff、effective date、SKU 适用域或服务端 affected cohort。即使规则未变化，页面也会把
全部精确匹配 SKU 报成需重评，违反“客户端不得重算/推断”的产品合同。

处理：`auto-fix`。新增服务端 rule-change evaluation，返回 change set、affected SKU、
unaffected SKU、原因、旧/新规则哈希、effective_at、Owner 和任务；无 diff 时显示
`no_data/not_applicable`，不得复用候选总数。

#### P0-PM-15：Portfolio Cockpit 把全部候选硬编码为 experiment

组合驾驶舱把 `exact_matched` 全部显示在 experiment，proven/growth/exit 固定为 0，
没有消费 `SellerOperatingSystem._portfolio()` 的 actual cash CM3 分桶结果。负利润、
已结算赢家和普通观察候选都会被错误投影，虽然文案承认缺 actual，数字仍冒充组合事实。

处理：`auto-fix`。页面只消费服务端 portfolio snapshot；无 actual 时显示
`unclassified/no_data`，不得归入 experiment。proven/growth/exit 必须分别带事实窗口、
结算周期、原因、资金和迁移任务。

### P1

#### P1-PM-01：前台必须逐动作解释 why allowed / why blocked

当前页用全局“当前运行不会上架”和 blocker 标签代替动作级决策，导致可做的观察、补证、
内容草稿与不可做的 publish/scale 混在一起。成熟度页面还会在策略 blocked 时显示默认
模式，存在误导。

必须为每个候选至少显示：

| 动作 | 当前期望 |
|---|---|
| observe / compare | 条件满足时 `allowed`，显示来源、时效和原因 |
| request evidence / RFQ | 条件满足时 `allowed`，显示 Owner 与下一步 |
| content draft / media brief | 事实足够时 `allowed`；权利/QA 不足只锁引用与发布 |
| request independent approval | 冻结快照齐全时 `allowed` |
| publish pilot | 缺独立批准或一次性 Permit 时明确 `blocked` |
| scale | 缺 24h/72h/7d、结算和现金 CM3 时明确 `blocked` |

每行必须返回服务端状态、why、缺失 Evidence、Owner、下一动作和目标工作区链接；客户端
不得自行推断。该 finding 修复并完成 PM 复审前不得 `APPROVED`。

处理：`auto-fix`。

#### P1-PM-02：首发 ICP 与六模式缺少可验证选择逻辑

从新手到集团同时覆盖，但没有首发优先级；六模式缺进入/退出条件的用户解释、动作差异与
真实效果证据。

处理：`ask-user` 冻结首发 ICP；`auto-fix` 模式对比、进入/退出条件和证据化迁移。

#### P1-PM-03：北极星指标尚未形成产品合同

只有成功指标字符串和“不以上品数为成功”的声明，没有可计算定义、窗口、目标、Owner、
仪表盘和反向指标。

处理：`auto-fix` 指标注册、服务端计算和漏斗/护栏视图。

#### P1-PM-04：六页 IA 是信息分栏，不是角色任务流

规则优势、组合驾驶舱、店群矩阵和增长指挥均缺对象级任务、Owner 和可执行下一步。

处理：`auto-fix`。优先保留少量真正承担 JTBD 的页面；若六 URL 保留，必须证明每页有
独立主要任务和完成标准。

#### P1-PM-05：缺桌面/390 与失败态浏览器 Evidence

CSS 规则不能替代运行验收，当前路由 404 更使验收不成立。

处理：`auto-fix`。完成六页桌面与 390px 路由/交互/错误态/无溢出回归和截图。

#### P1-PM-12：漏斗阶段的分母和状态语义不完整

当前 `observe` 是 Ozon 与供应 observation 的总和，`match` 是候选行数，
`evaluate` 实际使用 downside positive 数而不是已评估数；`stop` 没有进入漏斗，
`scale/reconcile` 固定为 0，即使候选已有回读/结算字段也不会反映。各阶段不是同一
cohort 的单调转化，用户无法定位是数据缺失、负利润、内容阻断还是治理阻断。

处理：`auto-fix`。冻结 cohort 分母，至少拆分
`raw observed → unique listing → identity eligible → exact cohort → evaluated →
downside positive → content ready → pilot eligible → selected → launched →
readback → reconciled → scale/stop`，每段返回转化率、流失原因和时效。

#### P1-PM-16：服务端 action readiness 已存在但前台隐藏

Global CN rule evaluation 已有动作级状态，batch 也有 automation stages，但
Seller OS 页面只展示整体 rule state、Pilot 总数和少量 blocker，没有暴露
`observe/content draft/approval/publish/scale` 各动作 readiness。这与
`P1-PM-01` 的产品要求直接相关。

处理：`auto-fix`。前台消费服务端 action readiness，不用整体状态替代；每个动作显示
状态、why、Evidence、Owner、SLA、下一入口。

#### P1-PM-17：成熟度表单不可用，缺验证、受控选项和隐私说明

表单直接暴露内部英文键；数值没有业务范围和单位，文本字段自由输入，没有错误提示、
帮助、数据用途、隐私/保留说明。客户端也没有把服务端字段错误映射回具体输入。

处理：`auto-fix`。使用中文问题和受控枚举，给出单位、范围、为何询问、证据来源、
隐私/保留和字段级错误；允许保存草稿而不把主观输入晋升事实。

#### P1-PM-18：六入口是静态壳，Growth Command 只显示首个候选

六个路由复用同一壳并用条件分支展示静态区块；Growth Command 使用
`batch.candidates[0]`，没有候选选择、组合、分页、任务队列或 cohort 操作。其七阶段是
静态文本，不是可完成的经营流。

处理：`auto-fix`。每个入口必须有独立主要任务、对象选择和完成标准；Growth Command
至少支持服务端排序后的 cohort、selected/waitlist、Owner/任务和状态推进，不能以首行
代替组合经营。

#### P1-PM-19：页面固定 `ozon-primary` 且缺店铺/主体 scope

Seller OS 与批量工作台请求、扫描 body、最新 run 均硬编码 `ozon-primary`；
后端 batch 在读取 Ozon observations 时也未按传入 `store_ref` 过滤。与此同时套餐宣称
支持 3、10、50+ 店，存在跨店数据污染和多店卖点不可用的双重问题。

处理：`auto-fix`。使用经鉴权的服务端 store/entity scope，店铺选择器只显示主体有权
访问的店铺；run、cohort、价格带、任务和 usage 均绑定 scope，并测试跨店隔离。

#### P1-PM-20：六页数据读取没有 catch / retry 恢复

初始化使用 `Promise.all(...).then(...)`，没有 `catch/finally`；网络拒绝、JSON 解析失败
或任一请求异常会留下永久“正在读取”或未处理 Promise。诊断请求同样没有异常捕获，
六页也没有明确重试动作。

处理：`auto-fix`。为 packs/batch/diagnosis 分别提供 loading、partial、error、offline、
retry 和 stale 状态；一个数据源失败不能吞掉另一个成功结果。

### P2

#### P2-PM-02：价格卡命名与价值表达不一致

`mid_market` 对应 Enterprise，`enterprise` 对应 Private；套餐只展示规模和治理限制，
没有结果价值、服务范围、SLA 和增购单价。

处理：`defer` 到 P0-PM-03 的商业模型冻结后统一修订。

## 13. 复审验收场景

1. **零数据首访**：桌面和 390px 打开六页均 200；显示真实 `no_data`、原因、Owner、
   重试和下一步，不展示演示 SKU。
2. **成熟度与模式**：只填部分事实时不猜分类；卖家事实完整但经营事实缺失时，分类可
   完成但模式必须显著 `blocked/no_data`，不得冒充推荐；表单完成率、Evidence 覆盖率和
   分类置信度分开计算，任意文本不能得到 `1.00` confidence。
3. **动作级可解释性**：同一候选显示 observe、补证、content draft 为可继续；
   publish/scale 因缺批准、Permit、Readback/结算而锁定，逐动作 why/Owner/链接完整。
4. **100 条观察漏斗**：真实或固定 Evidence-backed 批次报告实际 observation、精确
   Listing/cohort、downside 正、content ready、pilot eligible、selected、waitlist；
   数量不足时诚实显示瓶颈。重复快照不能重复计 SKU，漏斗各层使用同一冻结 cohort。
5. **精确匹配与利润语义**：错变体不匹配；checkout 观察仍非 Offer/actual；十五项
   baseline/downside 守恒；无 FX/费率/物流/退货证据时 blocked；跨店 observations
   不得进入当前 store run。
6. **内容交接**：事实足够可创建内容草稿；权利/Passport/QA 不完整时不可引用到
   Listing 发布，但不能阻断无副作用的补证和草稿准备。
7. **小流量 Pilot**：冻结 Listing、独立批准、一次性 Permit、1–3 件预算、Readback、
   Kill Switch 和补偿链可完整追溯，Agent 不能自批自发。
8. **24h/72h/7d 与结算**：回读失败进入 OperatingTask；只有结算/到账后进入 actual
   cash CM3；scale/stop 有停止条件和最大损失。
9. **套餐与用量**：计划状态、配额、当期使用量、超额行为、增购、升级/降级和账单沙箱
   可复验；所有套餐共享同一事实/利润真相内核。
10. **北极星**：服务端可计算并展示每周完成 7d 回读且进入结算对账的正现金 CM3
    Pilot SKU 数，同时显示人工/Agent 成本、最大损失、退款和越权护栏。
11. **规则与组合真实性**：规则页基于旧/新 registry diff 返回真实 affected cohort；
    无变更时不显示“需重评”。组合页从 actual cash CM3 服务端投影 proven/growth/
    experiment/exit，缺 actual 时显示 unclassified，而非把全部候选归为 experiment。
12. **Pilot limit**：`pilot_limit=1` 且存在多个 eligible 候选时恰好一个 selected，
    其余进入稳定 waitlist；重放、并列分数和 limit 变化不产生随机选择。
13. **浏览器交付**：六页桌面和 390px 截图齐全；390px
    `scrollWidth === innerWidth`；长标题、哈希、blocker 和矩阵不造成页面级横向溢出。
14. **合同一致性**：运行 OpenAPI、版本控制 OpenAPI、API 路由、Web fetch、匿名 401
    和版本号一致，容器重建后仍通过。

## 14. 最终决定

**REJECTED**

原因不是安全门过多，而是当前还没有把“什么现在可以做、什么为什么不能做”转化为最短
用户路径；同时交付容器缺六个页面、真实 run 为全零、商业套餐不可交易，无法证明
0.59 已可售卖或可支持真实 Ozon 经营闭环。

重新申请 Gate PM 的必要条件：

- 本报告全部 P0 关闭，或经经营负责人明确缩减发布范围并移除未交付的公开承诺；
- `P1-PM-01` 完成且由 PM 重新验收；
- cohort、pilot limit、漏斗、action readiness、store scope 和失败恢复均有服务端合同与
  产品验收；
- 六页/API/OpenAPI/桌面/390 运行 Evidence 完整；
- 至少一个真实 SKU 的小流量 Pilot 到 Readback，并明确实际利润仍等待结算时保持
  `partial/blocked`。
