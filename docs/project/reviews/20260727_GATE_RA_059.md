## 1. 执行摘要

0.59 的正确方向是把公开市场页、1688 checkout 观察和 Ozon Global CN 规则放在
Observation/Research 语义内，并继续声明不创建 Supplier Offer、正式 CM3、Permit 或
Ozon 写入。`MarketplaceObservationWorkspace` 也增加了 exact identity、数量、MOQ、
checkout 状态、税费/国内运费边界和 Evidence。

但当前实现不能通过 Gate RA：

1. 价格指数、费用成熟度和规则有效期尚未形成可审计、可按动作消费的稳定合同。
2. 批量 scanner 不是 Ozon cohort 聚合，只按一个 `candidate_key` 连接一个 Ozon 观察，
   再选最低展示价格的供应观察，存在机会排序系统性偏差。
3. `pilot_limit` 没有参与候选选择；`independent_approval_missing` 又被无条件加入 blocker，
   导致“eligible for approval”和“pilot ready”语义混淆。
4. 1000 条读取上限没有游标、分片和 cheap pre-score；规模声明超过了实际 Interface。
5. 策略包、费用 fallback 和漏斗均有“政策估计被用于精确排序/展示”的风险。
6. 目标后端测试实际失败，运行时 OpenAPI 与版本化快照不一致；没有 0.59 页面截图、
   容器 smoke、迁移回放或 PostgreSQL 并发证据。

因此本轮不得 APPROVED、不得进入 PR/合并或发布闭环。

## 4. 阻断 findings

### P0-RA-01：分段价格指数公式与 Decimal 边界未冻结

- 首轮实现使用单一 `buyer_price / external_lowest_price` 解释全部价格关系；评审过程中
  工作树开始改为分段公式，但规范、注册表、测试和 OpenAPI 尚未同步收敛。
- 价格为 0、负数、极小 Decimal、大 Decimal、等价价格、`1.02/1.05/1.06` 两侧一个
  最小精度单位、舍入前后跨 band、币种不一致均缺完整合同证据。
- 价格指数只能是 exact product cohort 的观察指标，不能覆盖 downside CM3。

处理：`auto-fix` 后 `re-review`。Owner：规则/利润模块 Owner。

验收：

1. 注册表明确分段公式、定义域、量化精度、舍入点和 band 的闭开区间。
2. 全部使用有限 Decimal；拒绝 0/负数/NaN/Infinity/跨币种无 FX。
3. 参数化测试覆盖每个边界 `-epsilon/exact/+epsilon`。
4. 同一输入在 Python、API JSON 和 PostgreSQL 重放结果一致。

### P0-RA-02：缺少完整的 action-scoped readiness 合同

- 首轮 `OzonGlobalRuleRegistry.evaluate()` 把 passport、content、price、quality、
  fee、settlement、API、analytics 全量聚合成一个 SKU 状态。
- 研究扫描、内容草稿、Pilot 审批、外部发布、结算和 scale 所需事实不同；全局状态会
  造成两类错误：前置动作被无关 settlement 阻断，或 `ready_with_constraints` 被调用方
  误解为可以发布。
- 评审过程中出现了 `actions/action_readiness` 修改，但目标测试已经失败，尚未形成稳定
  Interface。

处理：`auto-fix` 后 `re-review`。Owner：Ozon rules / Seller OS Owner。

验收：

```text
observe_research
candidate_score
content_draft
pilot_approve
external_publish
scale
settlement_reconcile
```

每个 action 必须声明 required/optional/not_applicable domains、独立 blocker 和权威语义。
顶层状态不得代替 action 状态；Batch 只能读取明确 action ID。

### P0-RA-03：fee estimated / accrued / reconciled 语义未稳定拆分

- 首轮 fee 只有一组 `commission_rate + settlement_status`，把订单前估算费率、发货后
  应计费用和结算到账费用混在同一 domain。
- 评审过程中虽出现 `estimate/actual_accrual/reconciled_cash` 结构，但运行时测试与
  OpenAPI 尚未收敛，也未见金额守恒、订单自然键和真实 Finance/Evidence 绑定。
- `delivered/returned/settled/reconciled` 不能作为一个可互换枚举。

处理：`auto-fix` 后 `re-review`。Owner：Finance / Profit Owner。

验收：

1. `estimated` 只读版本化 fee row，带 category/mode/price band/order date/effective date。
2. `accrued` 必须绑定 order natural key 和 Ozon accrual Evidence。
3. `reconciled` 必须绑定 settlement、bank/cash 与 Finance Entry Evidence。
4. 三种金额分别输出，不原地改标；不完整时不得显示 actual cash CM3。
5. 重复导入、退货、跨期、负向费用、冲销和未分摊均有守恒测试。

### P0-PM/RA-07：exact identity + variant 的 Ozon cohort 聚合缺失

- `_scan()` 只按一个哈希 `candidate_key` 匹配单条 Ozon observation 与供应 observation。
- 没有对同一 exact identity/variant 的多个 Ozon listing 形成 cohort，也没有样本数、
  中位数/分位数、店铺独立性、异常价、促销价和时效分层。
- 结果不能代表“市场价格带/竞争 cohort”，只能代表单观察对。

处理：`auto-fix`。Owner：Batch scanner Owner。

验收：同 exact identity/variant 至少形成服务端 cohort；错规格永不入组；输出样本数、
独立卖家数、价格语义、时间窗口和稳健统计；单样本只能 `partial/no_data`，不得精确排名。

### P0-RA-08：供应商只按最低展示价选择

- `_scan()` 对同 `candidate_key` 的供应观察按 `displayed_price` 排序并固定选择
  `options[0]`。
- 没有把 MOQ、购买数量、税、国内运费、包装重量、交期、供应商可靠性、Evidence
  等级和 FX 后 landed observed cost 放入选择。
- 这会把低价诱饵变体或高 MOQ 价格系统性选为“最佳供应商”。

处理：`auto-fix`。Owner：Supply/Scoring Owner。

验收：保留所有 exact supplier options；按统一 quantity 下的可复算 observed landed
cost 比较；缺任一关键边界时 `partial`；页面显示选中原因和被拒绝项，不把展示最低价
称为最佳采购成本。

### P0-PM-09：`pilot_limit` 未执行

- `pilot_limit` 被校验和回显，但没有截断候选、分配 Pilot 槽位或进入排序 fingerprint。
- 用户提交 1 与 100 可能得到同一 candidate readiness/列表。

处理：`auto-fix`。Owner：Batch workspace Owner。

验收：`pilot_limit` 只限制“eligible for approval/Pilot allocation”，不丢弃观察候选；
同一输入和 policy 产生确定性 allocation；改变 limit 使用同 idempotency key 必须
`IDEMPOTENCY_CONFLICT`，不能静默返回旧结果。

### P0-RA-13：Ozon Global CN 规则来源状态与真实生效日不具权威性

- 注册表多数规则标记 `official_source_configured`，但 `snapshot()` 只看
  `effective_from/effective_to` 就返回 `ready`。
- 多数 `effective_from` 等于评审日期 `2026-07-27`，没有证明是 Ozon 公布的规则生效日。
- 逐条规则没有 Evidence ID、原件 SHA-256、抓取时间、页面版本或独立复核。
- 官方帮助页本身可能包含多个不同生效日；例如物流页面按线路分别给出 2026 年 3/4 月
  的费率生效日期，不能用注册表创建日覆盖。

处理：`ask-user`（规则 Owner 确认）+ `auto-fix`。Owner：Compliance / Rule Owner。

验收：每条生产规则绑定可逐字节验证的官方 Evidence、真实 effective_from/to、
observed_at、source status 与 reviewer；`configured` 只能 `research_only/no_data`，
不能 `ready`；变更前后有 diff、影响 SKU、失效和重评记录。

### P0-RA-14：首轮 Verification Gate 已失败

- 后端目标测试 `2 failed`。
- OpenAPI 版本化快照与运行时不一致。
- 当前工作树处于并发修复状态，不能形成可审计候选 commit。

处理：`auto-fix`。Owner：工程 Owner。

验收：冻结候选 commit 后，目标测试、全量 pytest、OpenAPI snapshot、Ruff、secret
scan、Web test/build、迁移回放、单一 head、PostgreSQL/API/Web health、容器和浏览器
证据全部通过。

### P0-RA-15：Pilot readiness 与独立批准无法闭合

- 首轮 `_evaluate()` 无条件追加 `independent_approval_missing`，因此
  `pilot_ready = not blockers` 不可达。
- `prepare()` Interface 又没有 approval/plan ref；模块既不应创建 Approval，也无法读取
  现有独立批准。
- 当前字段实际混合了“满足经营输入、可进入审批”和“已批准、可进入 Pilot”。

处理：`auto-fix`。Owner：Batch/Governance Owner。

验收：拆分 `eligible_for_approval` 与 `pilot_ready`；前者不需要批准本身，后者只读取
现有冻结计划与独立 Approval/Permit readiness；同一 Agent 不可自批，模块仍不得创建
Permit 或执行 Ozon 写入。

## 5. P1 findings

### P1-RA-04：prelaunch 质量指标必须是 N/A，不是失败或通用 no_data

新 SKU 上架前没有 14 日订单、取消率、CSAT 和退货率是正常状态。质量 domain 应输出
`not_applicable_prelaunch`，并只在 scale/quality monitoring action 中成为 blocker；
不得阻断 research/content/pilot approval。

验收：零订单、首单、满 7 天、满 14 天、窗口跨日测试；N/A 不进入成功率分母。

### P1-RA-05：缺节假日日历时 dispute deadline 只能是 estimated

首轮 `_add_business_days()` 只跳过周末，却把结果显示为正式 `dispute_deadline`。中国、
俄罗斯及 Ozon 约定假日均可能改变工作日。

验收：有版本化法定/合同日历时输出 authoritative deadline；缺日历时输出
`deadline_status=estimated`、calendar blocker 和复核动作；测试跨春节、俄罗斯新年和
周末。

### P1-RA-06：Strategy Pack 缺版本化 policy registry / effective / tenant override / audit

`STRATEGY_PACKS`、`PORTFOLIO_POLICY` 和 Batch `POLICY` 为源码常量，同时包含商业套餐、
扫描额度、库存/广告额度和执行治理。它们没有 policy version、effective period、
tenant/store scope、批准人、override audit 或失效条件。

验收：建立一个版本化政策注册表（不建第二队列）；包和 override 都有
policy_id/version/effective_at/scope/actor/reason/hash；override 只能收紧；旧 run 重放
继续使用冻结版本；商业 entitlement 不得改变事实和利润内核。

### P1-RA-10：1000 条截断、无分页分片和 cheap pre-score

Batch 固定两次 `latest(limit=1000)`，随后才进行完整 Evidence 验证和十五项计算。超过
1000 的观察会静默缺失；也没有 cursor、分片快照或 cheap exact-identity pre-score。

验收：稳定 cursor/分片、总数与截断标志、批次水位、跨页去重；先 exact identity +
freshness + minimum fields cheap filter，再执行昂贵 Evidence/CM3；同一 as_of 可重放。

### P1-RA-11：fallback 佣金/费用不得参与精确排序

Batch POLICY 中佣金、物流、税费、退货等 fallback 被标记 `policy_estimate`，但其生成的
CM3 和 score 仍参与候选精确排序。即使 `cost_evidence_complete=false`，排序也制造了
虚假精度。

验收：含 fallback 的候选只能进入 estimate band/partial tier；不能和全 Evidence 候选
按小数精确比较；展示 fallback component、区间和敏感性；正式 fee row 缺失时不得称
downside profit 已证实。

### P1-PM-12：漏斗语义不完整

当前漏斗只展示 observe/match/evaluate/content_ready/pilot/scale/reconcile，scale 与
reconcile 固定 0；没有 unmatched、blocked、stop、eligible_for_approval、approved、
executed/readback 和 settled cohort，阶段之间也不保证单调。

验收：每个阶段定义入口、出口、去向和计数守恒；`previous = next + rejected + pending`；
scale/reconcile 只读真实任务、执行回读和结算，不硬编码。

### P1-RA-16：幂等与并发存在孤儿 Evidence 风险

`prepare()` 先查询 idempotency key，再在数据库事务之外创建 Evidence，最后插入带唯一
约束的 run。并发相同 key 时，两次都可能先创建 Evidence，其中一次 run 插入失败，留下
无法归属的 Evidence；相同 key 但 limits/policy 输入变化也会直接返回旧 run。

验收：idempotency key 绑定规范 request hash；不同输入返回稳定 conflict；并发两个请求
只有一个 run 和一份 run Evidence；在 Evidence/DB/link 任一故障点重试不产生孤儿或半成品。

### P1-RA-17：RBAC 与审计责任需要收紧

`POST /v1/batch-market-scans` 允许 `reviewer` 创建 run、Evidence 和 OperatingTask。
Reviewer 的职责应是独立复核，不应默认成为同一研究产物的作者；当前 run 也未见
Outbox/事件原子发布。

验收：operator 创建、reviewer/compliance 只读/复核；如确需 reviewer 发起，必须有
独立复核人约束。run 创建/失败/重放有 actor、request/trace、输入 hash 和 Outbox 覆盖
决策。

### P1-RA-18：0.59 NFR 与页面证据缺失

未看到 0.59 桌面/390px 实际截图、页面 loading/error/forbidden 运行证据、Next build、
容器镜像、真实 PostgreSQL 0052→0053 升级/回放、rollback rehearsal、P95 或 1000 条批次
资源上限数据。

验收：完成 AGENTS.md 全门禁，并记录 100/500/1000 条观察批次的延迟、内存、SQL 数量、
Evidence 验证次数、超时与中断恢复。

## 6. P2 / 范围边界

### P2-RA-19：当前不是多租户隔离实现

新表只有 `store_ref`，RLS 仅 `ENABLE`，未看到 tenant/legal entity key、数据库 policy
或 actor-to-store grant。MASTER_SPEC 仍明确多租户在 G7 前冻结，因此 0.59 可以仅作为
单经营主体实现，但页面、Strategy Pack 和对外宣称不得称为多租户 SaaS。

复审触发：第二法人或外部客户进入。届时必须新增 tenant/legal entity scope、授权映射、
跨租户查询/幂等/缓存/导出/审计隔离测试和迁移方案。

### P2-RA-20：ADR 所称五个内部 Module 尚未形成真实 seam

当前 scanner/scorer/classifier/variant/content 主要是一个类的私有方法；只有一个
implementation 时无需为了形式拆文件，但至少应把版本化 policy、observation query 和
rule evaluation 形成可替换且可测试的 internal seam。删除测试应证明复杂度集中，而不是
在 Router、Web 和 Seller OS 中重复。

## 7. 必须通过的端到端验收场景
