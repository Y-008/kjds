本文冻结商业目标、先后顺序、放行标准和任务边界，不证明任何真实经营结果。
“拿下俄罗斯市场”不得被解释为保证市场第一或保证盈利，而是按下述 Gate 逐步获得
一个可验证的细分市场立足点、正向现金贡献、可复制经营方法和付费软件客户。

## 1. 总决策

KJDS 采用同一经营内核驱动两个相互增强的商业引擎：

```text
俄罗斯真实店铺经营
  -> 形成可信订单、费用、结算、到账和复盘 Evidence
  -> 证明 KJDS 能止损、提效、降本和增加实际现金 CM3
  -> 沉淀案例、规则、模板和实施方法
  -> 向中国出海俄罗斯的卖家销售诊断与托管软件
  -> 客户反馈和付费能力反哺产品
  -> 扩大真实经营和软件收入
```

拍板如下：

1. 第一战场固定为俄罗斯 Ozon，不同时发动 Wildberries、第二国家和自有商城。
2. 第一软件客群固定为中国境内、面向俄罗斯 Ozon 的成长型卖家；俄罗斯本地卖家和全球多平台客户后置。
3. 第一商品不是“万能 ERP”，而是“俄罗斯 Ozon 利润真相诊断 + 受控经营工作台”。
4. G7 前采用单客户隔离部署或托管交付，不宣传自助多租户 SaaS，不建设第二事实源或第二审批系统。
5. 商业证明先于规模扩张：没有实际订单、退货、结算和银行到账闭环，不扩大采购、广告或软件利润承诺。
6. GMV、曝光和模型自述不是北极星；实际现金 CM3、现金周期、客户节省时间和付费留存才是。

当前商业状态不是“已经可以卖”。正式产品蓝图仍把全部价格标记为
`pricing_hypothesis/internal_preview/not_for_sale`。本文批准商业化方向和准备工作，
不绕过 Billing、Usage、Entitlement、发票/退款、单位经济、SLA、隔离部署和恢复验收。

## 2. `best_solution` 决策记录

### 2.1 被选方案

选择“自营实盘 + 服务先行的软件产品化”：先用 KJDS 经营一个受控 Ozon 竖切，同时
完成商业 Pilot 准备；`C0` 通过后才向首批设计伙伴销售付费诊断和托管工作台；达到 G7
与客户重复验证后再开放多租户 SaaS。

### 2.2 被拒绝或延期的方案

| 方案 | 处理 | 原因 |
|---|---|---|
| 直接发布通用多租户 SaaS | 延期至 G7 | 当前真实经营数据、客户验证、计费、隔离、SLA 和恢复证据不足 |
| 同时攻 Ozon、Wildberries、VK 商城和多个国家 | 拒绝 | 分散证据、合规、资金和研发，无法形成首个可复验闭环 |
| 只做自营、不卖软件 | 拒绝 | 放弃已有工程资产的高毛利复用和客户反馈飞轮 |
| 只卖软件、不做实盘 | 拒绝 | 容易退化为展示型 ERP，无法证明俄罗斯利润与执行边界 |
| 按 GMV 收费或承诺保证盈利 | 拒绝 | 激励扩大流水而非现金利润，且无法诚实归因 |
| 依赖第三方 ERP 作为真相源 | 拒绝 | 会破坏现有 Product、Fact、Evidence、Profit 和授权真相 |

### 2.3 失效条件

以下任一情况出现时必须重新评审本方案：Ozon 账户或收款路径不可合法持续；目标商品
无法满足产品合规、标识或物流要求；三次受控 Pilot 都不能形成正向实际现金 CM3；
首批十个合格客户访谈均不愿为诊断或托管试点付费；单客户交付成本长期高于可收收入；
或制裁、出口管制、平台条款变化使当前交易路径不可接受。

## 3. 北极星与结果口径

### 3.1 经营北极星

```text
actual_cash_cm3 = 银行实际到账
                  - 商品采购
                  - 国内与跨境物流
                  - 平台、仓储、广告、达人和促销费用
                  - 退款退货、税费、汇兑、资金占用、售后和损耗
```

该口径必须逐项绑定币种、FX 时间和 Evidence。预测、情景、计提、结算和实际到账永久
分开；`unknown` 不得按零处理。

### 3.2 软件北极星

首阶段使用“完成首次可信价值的付费店铺数”，而不是注册数：客户必须完成受权只读接入、
数据质量诊断、至少一个 SKU 的利润证据投影，并确认一个可执行的止损、补证或增长动作。

### 3.3 四类价值指标

| 目标 | 必须量化 | 禁止冒充结果的代理指标 |
|---|---|---|
| 获客 | 合格线索、诊断付费率、试点转年付率、获客回收周期 | 浏览量、无意向注册数 |
| 提效 | 首次价值时间、对账工时、Listing 周期、异常处理 SLA | 页面数、Agent 调用数 |
| 降本 | 广告浪费、错误采购、滞销占资、退款损失、工具与人工成本变化 | 未绑定基线的“节省百分比” |
| 增收 | 结算后增量现金 CM3、复购、缺货减少、可盈利 SKU 数 | 单独 GMV、ROAS 或订单数 |

所有“提升/降低”必须有同作用域基线、观察窗口、归因方法和证据等级。没有可比基线时只
报告当前值和 `no_data`，不得生成营销百分比。

## 4. 俄罗斯 Ozon 全业务闭环

### 4.1 闭环地图

| 环节 | KJDS 应交付的唯一结果 | 放行条件 |
|---|---|---|
| 市场与选品 | 规范化候选、需求/竞争证据、稳定商品身份 | 双来源、观察窗口、候选人工确认 |
| 商品合规 | 逐 SKU 产品要求、EAC/合格评定、标识、知识产权清单 | 合规负责人接受有效原件 |
| 供应采购 | 三报价、样品、变体、包装、尺寸重量和供应商备选 | 精确变体、实测、实际承担方原件 |
| 物流履约 | 路线、时效、计费重、清关、仓储和异常预案 | 报价与实单 Readback，不用网页估算冒充 actual |
| 商品内容 | 俄语 Listing、图片/视频、声明和版权 Evidence | Passport、QA、人工批准 |
| 定价利润 | baseline/downside/风险利润、保本价、预算上限 | 十五项成本、币种、FX 和证据完整 |
| 上架投放 | 冻结计划、审批、一次性 Permit、执行与回读 | Kill Switch、补偿、当前权限复验 |
| 订单库存 | 不可变订单时间线、库存守恒、补货建议 | 正式订单/库存 Fact，不猜库存 |
| 客服退货 | Case、退货退款、争议、SLA 和原因归因 | PII 隔离、独立审批、正式事件 |
| 结算到账 | 订单、平台费用、结算、银行到账多腿对账 | 同币种或有证据 FX，差异显式 |
| 增长复购 | Ozon 站内、VK/Telegram 的增量现金实验 | 同意、广告合规、止损、完整归因 |
| 组合复盘 | 保留/补货/调价/退出和模型评估 | 至少一个完整实际现金观察窗 |

现有工程已经覆盖其中大部分控制面和只读工作台，但“已实现接口”不等于“真实经营已
跑通”。任何时点的真实数据量、外部写状态和阻断以数据库、Evidence 和动态计划为准。

2026-08-02 Evidence 快照为：374 条源数据中 49 条 accepted、325 条 quarantine；18 个
现有候选全部 `needs_data`，0 Pilot，Actual Cash Profit 为 `no_data`，外部写关闭。
真实 Ozon 商品与财务只读链已跑通，说明账户/API 基础部分可用，但订单、退货、结算、
银行到账与人民币核销仍未形成闭环。18 个现有商品可用于修复和利润筛查，不自动满足
“三个新品候选”的需求证据、合规、三报价和供应链 Gate。

### 4.2 SKU 选择采用排除优先

首批 Pilot 优先低监管、低破损、低重量体积、低退货、变体清晰、非侵权、供应稳定且
售后简单的商品。以下类别默认不进入首批，除非合规负责人提供完整依据：食品、药品、
医疗器械、儿童用品、化妆品、危险品、带电池/无线/高功率电器、强制标识复杂品、易碎
重货、仿牌或授权不明商品。

该清单只是风险筛选，不替代逐 SKU 的 TN VED、技术法规、EAC/声明/证书、俄文标签、
“Честный ЗНАК”、知识产权、进口主体和平台类目要求判断。

### 4.3 渠道与库存顺序

1. Ozon 店铺自然流量、搜索和 Listing 转化先完成基线。
2. 首单采用最小批量或可撤销的跨境履约方案，避免在需求未证实时压本地库存。
3. 只有实际现金 CM3、退货率、时效和缺货损失连续通过后，才比较本地仓与跨境直发。
4. Ozon 站内广告只有在完整成本门和最大可承受 ACOS/CPC 已冻结后才可小额试验。
5. VK/Telegram 在站内闭环后接入，只优化 `incremental_cash_cm3`，并保留同意、广告标识、深链、优惠码、退款和奖励回拨证据。
6. Wildberries 只做只读市场研究；Ozon 可复制闭环通过前不启动正式第二平台工程。

复购当前不是已经跑通的正式事实。系统必须新增或接入一等的重复购买/结算 cohort
Evidence；若平台不允许稳定识别买家，只能使用合规的聚合复购指标，禁止自行拼接客户
身份或把触达事件冒充复购。

### 4.4 俄罗斯高风险人工门

| 风险 | 系统职责 | 必须人工确认 |
|---|---|---|
| EAEU/RU 产品法规 | 保存规则版本、SKU 绑定、证书/声明 Evidence 和到期提醒 | 适用法规、文件真实性、进口主体责任 |
| 强制标识 | 保存商品组、GTIN/DataMatrix、状态与物流交接证据 | 是否适用、何时贴码/入境/投入流通 |
| 海关与税务 | 保存 TN VED 候选、估值、原产地、税费与单证 | 最终归类、申报、税务处理 |
| 支付与制裁 | 持续筛查交易方、银行、产品、物流和受益人并留时间戳 | 律师/银行对交易路径的可接受结论 |
| 平台规则 | 版本化佣金、物流、广告、退货和 API 合同 | 账户当前合同及类目特殊条款 |
| 数据与营销 | 保存同意、用途、保留期、广告归因和撤回 | 俄数据/广告要求与跨境处理方案 |
| 消费者与知识产权 | 保存保修、退货、声明、商标和素材授权 | 本地消费者义务与权利有效性 |

法律、税务、制裁和产品认证属于动态高风险事实。Agent 可以检索和提示，不得批准、
伪造文件、替代执业意见或绕过平台/银行/海关控制。

## 5. 软件商业化模型

### 5.1 首个 ICP

首个理想客户是中国境内、已有 1–3 家 Ozon 店铺、50–500 个活跃 SKU、3–20 人团队和
合法收款路径，至少有一个经营周期数据，正在使用表格或多个割裂工具，无法回答 SKU
实际现金利润，且愿意提供受权只读数据并指定运营与财务负责人的成长型卖家。没有真实
账户、拒绝提供证据、经营违禁/侵权商品、要求黑产手段、要求 Agent 无审批直接写平台
或要求保证盈利的客户不进入首批。小白的数据与付费基础不足，大型集团的 SSO、SLA、
灾备和集成要求过高，均不作为首批主攻客群。

### 5.2 首个价值主张

> 把 Ozon 的商品、费用、库存、退货、结算和银行到账连成可追溯的 SKU 现金利润，
> 先找出正在亏钱和缺证据的地方，再用受控动作改善，而不是用 GMV 掩盖损失。

对外不得使用“稳赚”“全自动接管店铺”“AI 保证增长”“市场第一”等未经证明的承诺。

### 5.3 产品阶梯与定价实验

以下为首轮人民币、未税、非公开定价假设。`C0` 通过前不得报价成交、收款或形成应收：

| 产品 | 范围 | 价格假设 | 成功条件 |
|---|---|---:|---|
| 利润真相诊断 | 单店、只读数据、数据质量与 SKU 利润缺口、一次交付会 | 4,800 元/次 | 5 个工作日内形成客户接受的问题与下一动作 |
| 设计伙伴试点 | 单客户隔离、单店、最多 500 活跃 SKU、3 用户、90 天托管验证 | 19,800 元/店 | 完成首次可信价值、每周复盘并愿意续费 |
| 团队经营版 | 多角色、工作台、对账、任务与受控自动化 | 39,900 元/店/年 | 至少三家设计伙伴重复验证后发布，实施/连接器另计 |
| 企业版 | 多主体、SLA、集成、审计、灾备和专属实施 | G7 后单独报价 | 隔离、恢复、支持成本和法务通过 |

若采用效果费，只能基于双方接受的“增量实际现金 CM3”公式、基线、窗口和数据源，且
设置费用上限和争议处理；不得按 GMV 或模型预测收取效果费。

### 5.4 获客飞轮

```text
自营店真实 Evidence
  -> 匿名化案例与利润诊断清单
  -> 卖家社群 / 服务商 / 物流与财税伙伴 / 内容获客
  -> 资格筛选
  -> 付费诊断
  -> 设计伙伴试点
  -> 年付经营版
  -> 复购、转介绍和伙伴渠道
```

第一阶段不烧大额品牌广告。先用创始人销售、现有卖家圈、俄罗斯物流/财税/认证服务商
和高意向内容获得十个合格访谈；免费内容只做筛选，不免费完成完整诊断。

### 5.5 软件从“能用”到“能卖”的缺口

P0，首个付费设计伙伴前必须具备：

- 把当前未提交工程收敛为可发布版本：版本号、镜像、变更日志、迁移清单、SBOM、验收报告和可回滚标签一致；
- 不把当前开发 Compose 冒充生产：完成 TLS/反向代理、秘密管理、日志采集、健康告警和生产拓扑；
- 首批采用一客户一套应用、一数据库、一密钥域，完成备份恢复、升级回滚和数据全量导出；
- 客户/店铺准入、只读凭证授权、撤销、权限检查和健康诊断；
- 可重复的数据导入、映射、质量报告、演示数据与首次价值引导；
- 角色、审批、审计、Evidence、PII 脱敏、日志和支持工单边界；
- 最小 Subscription/Entitlement/Usage Ledger、配额、Invoice/Payment/Refund 和 `active/grace/read_only/closed` 生命周期；
- 合同、隐私、数据处理、数据保留/删除、安全说明、事故通知和支持 SLA；
- 产品使用、错误、首次价值、AI/媒体/存储/人工支持成本和客户结果的可观测指标；
- 对外演示、报价单、实施清单、验收单、案例模板和退出/数据返还流程。

P1，三家设计伙伴重复验证后建设：

- 标准化租户/环境供应、版本兼容矩阵、自动升级与恢复演练；
- CRM 漏斗、线索归因、续费预警、客户健康和伙伴分成；
- 套餐配额、许可证、发票/收款对账和年度合同运营；
- 公开状态页、正式 SLA、客户管理员控制和审计导出。

P2，仅在 G7 放行后建设：

- 自助注册、试用、订阅、自动计费和多租户供应；
- 跨客户基准或模型学习；必须取得明确同意、匿名化并满足数据边界；
- 第二平台、第二国家、开放生态和 Agent 市场。

商业外壳不得拥有商品、订单、利润、Evidence、审批或 Permit 真相。CRM、计费和客服可
保存自己的商业元数据，但必须通过受控合同引用 KJDS 客户/租户标识，不得复制经营账本。

## 6. Gate 路线

90 天只作为市场验证窗口，不是工程完成承诺；任何 Gate 未通过就停留、补证或退出。

| Gate | 验收标准 | 未通过时 |
|---|---|---|
| C0 Commercial Pilot Gate | 稳定 Release、隔离生产部署、最小 Billing/Usage/Entitlement、发票退款、单位经济、合同/DPA、SLA、备份恢复和退出导出全部验收 | 保持 `not_for_sale`，不得报价成交、收款或形成应收 |
| R0 经营权威 | 主体、Ozon 账户、最小权限、收款、物流与合规 Owner 有有效 Evidence | 不上架、不投放、不收集敏感凭证 |
| R1 三 SKU 真相 | 三个候选完成身份、合规、三报价、样品/重量、十五项成本和 downside CM3 | 淘汰或补证，不采购 |
| R2 最小 Pilot | 至少一个 SKU 获人工批准，预算、止损、Permit、回读和补偿已演练 | 保持只读/草稿 |
| R3 首个现金闭环 | 订单、退货窗口、平台结算、银行到账和实际现金 CM3 可对账 | 不扩大库存/广告 |
| R4 可复制经营 | 至少三个独立观察周期通过利润、时效、退货和现金门 | 调价、换品或退出 |
| S0 可卖合同 | ICP、诊断包、报价、合同、演示、实施和验收资产齐全 | 不公开销售承诺 |
| S1 首个付费伙伴 | 合格客户付款，完成首次可信价值并签署验收/问题清单 | 修正 ICP/产品/价格 |

| S4 SaaS 放行 | 项目 G7、多租户安全/恢复/法务/计费 Gate 全部通过 | 继续单客户隔离交付 |

### 6.1 90 天最小实盘时间包络

## 7. 多任务调度与写域

### 7.1 当前调度

| 任务 | 唯一职责 | 允许写域 | 禁止事项 |
|---|---|---|---|
| 总控任务 | 商业目标、Gate、依赖、冲突、集成与最终验收 | 本合同、决策与最终集成 | 与研发任务争写共享代码 |
| 真实经营工程任务 | FX、成本、变体、订单/结算/到账和利润 Gate | 独立深模块、测试、必要工程 Evidence | 自定套餐、价格和营销承诺 |
| 前端体验任务 | 完成现有 frontend-toolkit 页面和构建验证 | 该功能页面、样式、元信息 | 未冻结的官网、计费、注册或利润宣传 |

### 7.2 新任务创建条件

按以下顺序新增任务，不按“能开多少窗口”决定：

1. `COM-001 最小销售包`：本合同冻结后，产出客户资格表、诊断交付物、报价、合同清单和成交页真实文案。
2. `COM-002 单客户交付底座`：真实经营工程稳定、写域可隔离后，建设部署/备份/升级/导出/许可证/支持能力。
3. `RUS-001 合规证据矩阵`：三个真实候选 SKU 与进口主体明确后，逐 SKU 建立动态法规和文件门。
4. `COM-003 首个设计伙伴`：销售资产和单客户交付底座通过后启动，不由研发伪造客户。
5. `COM-004 SaaS 产品化`：三家重复付费且 G7 接近通过后才创建。

每个任务开始前必须填写 `T06_AGENT_HANDOFF.md`：唯一目标、前置 Gate、允许文件、禁改区、
事实来源、验收命令、Evidence、回滚点和唯一下一动作。`api.py`、`runtime.py`、共享领域对象、
Alembic、`MASTER_SPEC` 和动态计划只允许单一集成人在合流窗口修改。

### 7.3 WIP 与集成规则

- 每个任务同时只有一个 `IN_PROGRESS` 主目标；无验收合同不得开新任务。
- 并行任务必须拥有互不重叠写域；共享 Schema 先冻结 ADR/合同再开发。
- 工程完成、真实经营完成、客户验收和商业成功是四种不同状态，不得互相冒充。
- 每次合流只处理合同、冲突、验证和 Evidence，不顺手扩大需求。
- 连续两轮没有提高当前 Gate 通过率的任务降级或停止。
