# BAS-069 最佳方案选择合同

## 结论

KJDS 已把“所有重大方案选择最佳解决方式”从口头偏好固化为版本化 `best_solution`（别名 `/best`）决策合同。合同只负责形成可审计的分析边界，不获得改价、投放、采购、付款、上架或其他经营执行权。

## 选择规则

1. 先检查安全、证据、权限、法律/合规、预算、验收、回滚和事实真源等硬约束；违反任一硬约束的方案直接淘汰。
2. 只在可行方案之间比较：长期风险调整价值、证据质量、总拥有成本、最大损失、可逆性与回滚、价值实现时间、运维适配、维护和替换成本。
3. 可行时包含“不行动/延期”方案；不把最新、最复杂、功能最多或代码最少自动当作最佳。
4. 不对不可公度维度使用等权总分制造虚假精度；必须写明淘汰理由、敏感性、失效条件、复审触发和审批要求。
5. Ponytail/YAGNI 只在最佳可行方案确定后删除无价值复杂度，不覆盖安全、证据或长期价值。

## 当前三类选择复核

### Ozon 财务事实来源

- 选择：Ozon 官方原始导出/API Evidence → 独立来源复核 → 版本化会计分类 → 多腿对账。
- 淘汰：把萌啦等计算器直接作为财务事实；原因是缺少账户原始结算、银行、税单和稳定字段血缘。
- 保留：第三方计算器只做 C/D 级交叉检查。
- 失效条件：第三方取得可验证一手授权、版本化合同并通过真实样本对账，或 Ozon 官方来源合同发生变化。

### 第三方选品与 ERP 接入

- 选择：先手工导出进入既有 Evidence 收件箱，形成可测吞吐/错误基线后再评估 Open API 或插件。
- 淘汰：立即安装所有连接器；原因是当前瓶颈是三个真实候选与一手证据，不是采集吞吐，且会扩大凭证面和双事实源风险。
- 失效条件：手工导入量、延迟或错误率成为实际瓶颈，且 API 许可、最小权限、撤销、审计和对账通过。

### 当前技术架构

- 选择：继续使用 PostgreSQL、现有控制面服务、Evidence、审批、Outbox 和既有 Worker。
- 淘汰：现在新增 Kafka、Temporal、向量数据库或第二事实库；原因是没有 SLO/吞吐证据支持，新增组件会提高运维与故障传播成本。
- 失效条件：长期任务恢复、并发、吞吐或检索质量形成量化瓶颈并通过 ADR/PoC 验收。
