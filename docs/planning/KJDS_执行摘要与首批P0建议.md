# KJDS 执行摘要与首批 P0 建议

版本：V1  
用途：将现有战略文档、项目总纲和任务总库压缩为一期唯一执行入口。  
范围：Ozon 俄罗斯市场，不超过 3 个真实 SKU，13 周受控经营验证。

## 一、执行结论

KJDS 一期不应以“建成完整 AI 跨境电商平台”为目标，而应证明一条可审计、可复跑的真实经营闭环：

> 合法准入 -> 商品上架 -> 真实订单 -> 履约/退货 -> 平台结算 -> 银行到账 -> 订单级 CM3 -> 经营决策

一期成功不等于所有 SKU 都盈利。只要系统能用真实证据准确解释利润或亏损，并及时得出 Scale、Iterate、Pivot 或 Stop 结论，就完成了核心验证。

一期唯一 North Star：

- 不超过 3 个真实 SKU 完成端到端闭环；
- 至少 100 个真实订单的费用解释率达到 99.5%；
- 月度“平台结算－银行到账”汇总误差不超过 0.3%；
- 完成 2 个预注册、可停止、可回滚的受控经营实验；
- 至少 1 个 SKU 在退货后 CM3 为正，或全部 SKU 都形成证据充分的停止结论。

## 二、系统边界

必须自研并保持确定性的核心：

- 商品、SKU、订单、批次和平台对象的统一身份；
- 原始证据、可信等级、双时间和数据血缘；
- CM1-CM4、费用字典、订单分录和三方对账；
- 合规状态机、有效期和硬阻断；
- Command-Approval-Result、幂等、复读、补偿和审计；
- 实验登记、指标、预算、停止和回滚。

一期应采用或薄适配的能力：

- 工作流、对象存储、可观测性、策略引擎、模型接口、文档解析和后台界面；
- Ozon 接入采用官方 API/报表优先的薄客户端，不把第三方 SDK 当权威事实来源。

AI 的职责：研究、抽取、归类候选、提出建议、解释异常、生成实验候选。

AI 不得负责：生成金额事实、最终合规放行、自行扩大权限、绕过审批执行写操作、静默修复缺失事实。

## 三、首批 10 个 P0

任务库中约 58 项被标记为 P0，仍不具备真实排期意义。首批只激活以下 10 项，其他任务保持排队状态。

| 顺序 | 任务 | 直接产出 | 完成判据 |
|---|---|---|---|
| 1 | GOV-001 经营宪法与反需求清单 | 一期目标、禁止项、成功/停止条件 | 业务、财务、合规、技术共同批准；正文控制在可执行范围内 |
| 2 | GOV-003 RACI 与审批权限 | 高风险动作责任人、替岗和紧急接管表 | 每个高风险动作只有一个最终负责人；发起和批准分离 |
| 3 | OSS-001 开源许可证与准入政策 | 许可证分级、版本锁定和退出规则 | 未准入组件不能进入一期核心链路 |
| 4 | DAT-001 统一商业语义与商品身份 | 术语字典、唯一键和平台映射 | 3 个 SKU、供应商 SKU 与 Ozon SKU 无歧义对应 |
| 5 | GOV-007 数据分级与跨境使用规则 | 数据分类、存储、模型访问和保留矩阵 | 凭证、个人、财务和生产数据默认不进入外部模型 |
| 6 | FIN-001 财务 Oracle 与费用字典 | CM1-CM4 定义和费用唯一归属 | 金额口径版本化；未知费用进入隔离，不归入“其他”掩盖 |
| 7 | CMP-001 SKU 合规档案与状态机 | Compliance Passport 和硬阻断状态 | LLM 无权把 SKU 改为 PASSED；过期和缺证据可阻断 |
| 8 | GOV-002 Build/Buy/Partner 边界 | 能力边界、弃选理由和退场方案 | 一期不重复建设 ERP、WMS、BI、工作流或 Agent 框架 |
| 9 | OZN-001 店铺只读配置快照 | 账户、合同、履约、结算、权限等真实证据 | 核心配置有时间戳和证据，全程不执行写操作 |
| 10 | DAT-002 可信等级、双时间与证据引用 | 事实等级、有效时间、记录时间和冲突规则 | 低可信数据不能覆盖官方事实；历史决策可重建 |

并行限制：同一时间最多 3 项处于“进行中”，每项必须有单一 Owner、时间盒、验收证据和未完成原因。

首批 10 项完成后，第二批优先进入：RUL-001、OSS-003、OZN-003、CMP-002、DAT-003、DAT-004、OZN-004、FIN-002、DAT-005、HAR-007。

## 四、13 周推进建议

### 第 1-2 周：冻结边界和真实事实

- 完成首批 10 个 P0，不追求大而全的制度文档；
- 获取 Ozon 店铺、合同、履约、结算和权限的只读证据；
- 确定 3 个候选 SKU，并尽早启动外部合规、银行、物流和报关确认；
- 验证现有工程基线、数据库迁移、回滚、API/DB/Web 冒烟测试。

退出条件：目标、责任、数据、财务和合规口径已冻结；真实店铺路径无致命阻断。

### 第 3-6 周：打通最窄纵向链路

- 只实现 3 个 SKU 所需的 Ozon 只读端点和报表导入；
- 建立原始证据、数据合同、订单状态、订单分录和初步对账；
- 完成 SKU 三类 Passport 和红线合规预审；
- 先用历史样本和测试单回放，再进入真实写操作。

退出条件：一笔订单能从平台事实追溯到原始证据，并计算可复核的 CM3。

### 第 7-10 周：真实订单和资金闭环

- 在审批、幂等、复读和 Kill Switch 可用后执行受控上架；
- 跟踪真实订单、取消、退货、赔偿、结算和银行到账；
- 逐项隔离未知费用和状态冲突，不允许静默补值；
- 每周滚动更新 13 周现金流和 SKU 最大损失。

退出条件：至少一笔真实订单完成到账核销，第二笔或第二 SKU 可重复执行。

### 第 11-13 周：实验和投资判断

- 建立稳定经营基线；
- 预注册并执行 2 个有限变量实验；
- 完成 100 单财务验收，输出每个 SKU 的 Scale/Iterate/Pivot/Stop 结论；
- 只有通过 Gate 4 后，才讨论扩 SKU、扩平台或扩 Agent。

## 五、主要风险与停止条件

当前最大风险不是模型能力不足，而是范围膨胀、真实数据不足和外部责任未落实。

出现以下任一情况，应停止相关 SKU 或暂停自动化：

- 商品、主体、支付、物流或合规路径存在未解决的禁止项；
- 关键事实没有官方、实测或责任人证据；
- 订单费用长期无法解释，或对账差异无法归因；
- 写操作缺少审批、幂等、复读、补偿或紧急停止能力；
- SKU 在压力情景下超过批准的最大现金损失；
- 团队开始用页面数量、Agent 数量、GMV 或代码完成度替代经营证据。

## 六、文档治理建议

后续文档只保留五层：

1. 经营宪法：稳定原则、目标、禁止项；
2. 一期执行摘要：当前范围、Gate 和首批 P0；
3. Backlog：任务、依赖、Owner、状态和验收；
4. ADR/数据字典/财务口径：具体技术与业务决策；
5. Runbook/证据包：实际操作、事故处理和验收材料。

原有长篇 Word 文档作为研究资料归档，不再同时充当执行计划。任何新需求先进入需求/假设账本，经 Gate 决定后再进入 Backlog。

## 七、总体判断

这套方案的方向是成立的，尤其是“证据优先、利润真值、合规硬门、受控执行、实验学习”五个原则。真正决定成败的，不是是否搭出完整 Agent 组织，而是能否在 13 周内把 3 个真实 SKU 和真实资金流做成一条可复核的窄闭环。

建议暂缓所有与一期闭环无直接关系的宏大能力，包括多平台统一、复杂知识图谱、自主数字 CEO、大规模多 Agent 组织和预测型世界模型。它们应由真实订单数据证明有必要后再建设。
